## 1. 产品目标

**一句话定位**：做一个开源、模块化、可扩展的 macOS 剪贴板管理器，既是一款优秀的剪贴板效率工具，更是一个让用户能持续叠加自研功能模块的「地基软件」。

**核心目标：**

1. **剪贴板效率刚需**：可靠地完成剪贴板监控、历史记录、搜索、全局快捷键四大核心能力，体验对标主流商业软件（iCopy、Paste、Maccy 等）。
2. **模块化 / 插件化地基（P0 架构约束）**：从第一天起就把「功能模块 / 插件框架」作为一等公民，任何第三方功能（右键工具、文件转换等）都通过标准化的模块接口挂载，核心本体保持轻量、稳定、可独立演进。
3. **开放与可移植**：开源可审计，代码结构清晰，便于社区贡献；在保证 macOS 优先的前提下，不写死平台能力，为 Windows / Linux 预留抽象层。
4. **数据可掌控**：剪贴板历史与配置支持多端同步，且同步后端可选（自建 / WebDAV / S3 兼容），让用户自己掌握数据归属。
5. **隐私与安全优先**：默认不上传数据、不采集遥测；对密码类剪贴板内容做识别与保护（脱敏 / 忽略 / 加密），建立用户信任。

## 2. 目标用户与场景

### 用户画像

| 画像 | 描述 | 核心诉求 |
| --- | --- | --- |
| 效率型开发者 / 极客 | 每天大量复制粘贴代码、命令、路径，喜欢快捷键与可定制 | 快、可搜索、可脚本化、开源可审计 |
| 自研工具爱好者 | 想把「右键工具」「文件转换」等自研能力装进一个常驻的系统级底座 | 模块化、可扩展、方便挂载自研模块 |
| 多设备办公用户 | 在 Mac 与笔记本/其他设备间切换，希望剪贴板内容同步 | 多端同步、数据可靠、可自建后端 |
| 隐私敏感用户 | 对云端剪贴板数据被第三方读取高度警惕 | 本地优先、同步可自选、敏感内容保护 |

### 典型使用场景

1. **高频复制粘贴**：用户连续复制多段代码/文本，通过全局快捷键调出历史列表，快速回贴，无需来回切换窗口。
2. **历史找回**：复制过一段重要内容但已被新复制覆盖，通过搜索关键词在历史中找回。
3. **密码/敏感信息保护**：复制了密码、token 后，希望该内容不进入历史或被自动脱敏/加密。
4. **跨设备接力**：Mac 上复制一段文字，希望在另一台设备上直接粘贴（通过自建或自选同步后端）。
5. **⭐ 剪贴板工具作为系统级地基（核心场景）**：用户把 ClipBase 当作常驻后台的「底座」，随后把自研的「鼠标右键工具」「文件转换」等功能，以模块方式安装进来——ClipBase 负责模块的安装/启用/更新/隔离与统一的菜单/快捷键入口，各模块专注自身业务逻辑，用户在一个统一入口下管理和调用所有自研能力。

## 3. 用户故事

1. 作为**开发者**，我希望剪贴板历史能被全局快捷键随时调出并快速搜索回贴，以便不打断编码心流。
2. 作为**隐私敏感用户**，我希望复制密码/token 时内容默认被识别并排除出历史，以便避免敏感信息泄漏。
3. 作为**多设备用户**，我希望历史与配置能同步到我的其他设备，以便在不同 Mac 间无缝接力。
4. 作为**自研工具爱好者**，我希望以标准化的方式安装/启用一个「功能模块」（如右键工具），以便把自研能力快速挂进底座并获得统一入口。
5. 作为**模块开发者**，我希望有清晰的模块接口规范与隔离边界，以便开发的功能模块不会拖垮或破坏剪贴板核心本体。
6. 作为**开源社区用户**，我希望代码结构清晰、文档齐全、协议宽松，以便放心使用并贡献代码。
7. 作为**普通用户**，我希望开箱即用、默认配置合理，以便不折腾也能立刻获得比系统剪贴板更好的体验。

## 5. 核心用户流程

### 5.1 主流程：复制 → 监控 → 入历史 → 搜索 → 回贴

```
1. 用户在任意 App 中「复制」（Cmd+C）
   └─ 系统剪贴板变更事件被 ClipBase 监听捕获
2. ClipBase 读取剪贴板内容与类型
   └─ 判断：是否为敏感内容？
        ├─ 是 → 按策略忽略/脱敏/加密（不进入明文历史）
        └─ 否 → 写入历史列表（含时间戳、来源 App、类型）
3. 用户需要找回/回贴时，按下全局快捷键
   └─ 弹出主窗口（历史列表）
4. 用户输入关键词搜索 / 直接浏览
   └─ 即时过滤展示匹配条目
5. 用户选中目标条目（回车/点击）
   └─ ClipBase 将内容写回剪贴板并触发粘贴到当前 App
6. （可选）内容按需参与多端同步（若同步开启）
```

### 5.2 安装 / 启用一个功能模块

```
1. 用户进入「设置 → 模块」页，或点击托盘菜单「管理模块」
2. 选择安装方式：
   ├─ 从本地文件/目录加载模块包
   └─ （P1）从模块市场/仓库安装
3. 系统校验模块包：签名、版本、依赖、权限声明
   └─ 展示模块所需权限清单，用户确认授权
4. 模块安装完成 → 默认「禁用」状态（安全默认）
5. 用户点击「启用」→ 模块加载进独立沙箱/进程
   └─ 模块注册自己的入口（托盘菜单项 / 快捷键 / 设置项）
6. 用户从统一入口调用模块功能（如：右键工具、文件转换）
7. 用户可随时「禁用/卸载」模块，不影响剪贴板核心
```

## 7. 多端同步方案

| 方案 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| **A. 自建服务**（轻量自托管后端） | 完全掌控、可做账号/权限/协作、可控成本、隐私最好 | 用户需自部署、维护成本高、实现工作量大 | 进阶用户 / 团队 |
| **B. WebDAV**（坚果云/Nextcloud/自建 WebDAV） | 标准协议、现成网盘可用、实现简单、无需自建 | 依赖第三方网盘、并发/实时性一般、冲突处理弱 | 个人用户、快速落地 |
| **C. S3 兼容存储**（MinIO/R2/OSS/COS 等） | 生态成熟、对象存储便宜、可扩展、密钥鉴权简单 | 需用户自备存储桶与密钥、实时推送需额外机制 | 有云资源的中高级用户 |

**推荐**：**分阶段落地，首选 WebDAV（B）作为 P0 起步**，同时把「同步后端」抽象成接口层，为 A / C 预留实现。

**理由**：
1. WebDAV 是开放标准、市面上大量现成网盘（坚果云、Nextcloud）直接可用，**用户零部署成本**，最贴合「开箱即用」目标。
2. 实现成本最低，能快速打通「本地优先 + 可同步」的 P0 闭环。
3. 通过后端接口抽象（sync provider 接口），后续可平滑追加自建服务（A）与 S3 兼容存储（C），满足进阶用户「数据自掌控」诉求。
4. 所有方案统一叠加**端到端加密**（SYNC-04），保证即使走第三方网盘，内容也不可读。

## 8. 待确认问题

| # | 待确认项 | 选项 / 说明 | 影响 |
| --- | --- | --- | --- |
| 1 | **开源协议** | MIT（宽松、利于传播）vs Apache-2.0（含专利条款、更规范） | 品牌与社区策略 |
| 2 | **正式命名** | 建议：① ClipBase（简洁直白）② ClipForge（强调「锻造/可扩展」）③ ClipDock（强调「底座/停靠」） | 品牌、仓库名 |
| 3 | **同步后端首选** | 推荐 WebDAV 起步；是否要自建服务纳入 P0 或延后 | 架构工作量与排期 |
| 4 | **账号体系** | 是否需要账号体系？还是「免账号 + 端到端加密 + 自选后端」？ | 后端复杂度、隐私定位 |
| 5 | **模块分发形态** | 首版是否只做「本地加载模块」，模块市场/在线仓库延后？ | 模块框架范围 |
| 6 | **敏感内容识别策略** | 默认「忽略密码类」还是「脱敏保存」？是否需要本地 AI 识别 | 隐私体验 |
| 7 | **历史容量上限默认值** | 例如：2000 条 / 500MB 上限，是否可调 | 性能与存储 |
| 8 | **图片/文件类型的 P0 范围** | P0 是否仅文本，图片/文件延后到 P1？ | 首版范围收敛 |
| 9 | **文件转换模块（filee）依赖** | 后续从用户本机 filee 源码提取，需明确其依赖与许可 | 模块开发规划 |

## 附：给架构师的约束摘要

- **模块/插件化是 P0 架构底线**，核心剪贴板本体与功能模块必须强解耦、可隔离、可独立演进。
- 平台能力需抽象，macOS 优先但不得写死，为 Windows/Linux 预留。
- 同步层做成 provider 接口，首版落地 WebDAV，预留自建服务与 S3 兼容。
- 隐私默认值：不上传、不采集、敏感内容可排除/加密。
