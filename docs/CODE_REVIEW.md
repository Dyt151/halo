# 代码审查标准与流程

> 本文件定义 ClipBase 的代码审查（Code Review）标准与流程。目标：**在缺陷进入 `main` 之前拦截它**，并让每一次审查都成为一次教学，而不是一次把关。

适用对象：所有向本仓库提交代码的人（作者与审查者）。本文档是强制约定，不是建议。

---

## 一、总则

1. **审查聚焦于实质，而非风格。** 我们关心：正确性、安全、可维护性、性能、测试。缩进、命名偏好这些交给工具（rustfmt / 编辑器配置），除非没有工具覆盖，否则不进入人工审查。
2. **审查是教学，不是挑刺。** 每一条评论都要说清「为什么」，而不是只说「改一下」。
3. **小步快跑。** 单个 PR 控制在 400 行以内（测试与生成物除外），超了先拆小。
4. **一次给全。** 审查者在一次 review 里把问题全部列出，不要挤牙膏式地一轮挤一条。
5. **CI 绿是审查的前提。** 红线（CI 失败）的 PR 不进入人工审查，先让作者修绿。

---

## 二、审查标准

### 2.1 严重等级分级

所有审查意见必须标注等级。三个等级语义如下：

| 等级 | 标记 | 含义 | 是否阻塞合并 |
| --- | --- | --- | --- |
| Blocker | 🔴 | 必须修复：安全漏洞、数据丢失/损坏、竞态/死锁、破坏 API 契约、关键路径缺错误处理 | 是，合并前必须解决 |
| Suggestion | 🟡 | 应当修复：缺输入校验、命名或逻辑混乱、重要行为缺测试、明显性能问题（N+1、不必要的拷贝）、应抽取的重复代码 | 强烈建议，作者可说明理由后不改 |
| Nit | 💭 | 可选：风格不一致（无工具覆盖时）、微命名、文档缺口、替代方案探讨 | 否，作者自行取舍 |

**判定经验**：拿不准 🔴 还是 🟡 时，问一句「这个缺陷上线后，最坏会发生什么」。会造成数据损坏、安全事故、功能不可用 → 🔴；只是变丑、变慢一点点、以后可能难改 → 🟡 或 💭。

### 2.2 六维审查检查清单

审查者逐项过一遍。作者提交前也用同一份清单自审。

#### ① 正确性

- [ ] 空值 / 边界条件：空列表、空字符串、`null`/`undefined`、越界下标、除零。
- [ ] 状态机与异步竞态：回调里读取的闭包值是否是最新状态？（本项目踩过：搜索防抖未落地就回车，读到上一轮结果）
- [ ] 幂等与重复触发：同一操作连点两次是否安全？事件处理是否可能被重复执行？
- [ ] 错误分支真的处理了错误，而不是「打日志后继续装没事」。
- [ ] 跨平台假设：代码是否默认了某个平台才成立的行为？

#### ② 安全

- [ ] 用户/剪贴板内容进 HTML 前是否经过 `sanitize`？（本项目剪贴板内容本质是外部不可信输入，XSS 是首要威胁）
- [ ] 敏感内容（JWT、密钥、密码）是否走了脱敏/加密策略，而非明文入库或明文写日志？
- [ ] 文件路径是否做了目录穿越 / 符号链接防护？（TOCTOU 检查在 `core/` 已有先例，新代码要跟上）
- [ ] 注入类风险：SQL 是否参数化？Shell 是否避免字符串拼接？
- [ ] 权限/能力边界：Tauri 侧是否校验了来自前端的调用参数？

#### ③ 可维护性

- [ ] 决策逻辑是否可测试？内嵌在 React 组件里的状态机应抽成纯函数（见 `src/lib/panelKeys.ts`、`ringState.ts` 的先例）。
- [ ] 命名是否自解释，6 个月后的自己能否一眼看懂？
- [ ] 是否有重复代码应抽取；是否过度抽象反而更难读？
- [ ] 函数是否过长、职责是否单一？

#### ④ 性能

- [ ] 是否有 O(n²) 的嵌套循环、不必要的重复计算（可提前缓存）。
- [ ] 是否有 N+1 查询、循环里做 IO。
- [ ] 热路径（剪贴板轮询、环形盘拖拽渲染）是否做了必要的开销控制？虚拟滚动是否被无意绕过？
- [ ] 是否有不必要的深拷贝 / 大对象序列化。

#### ⑤ 测试

- [ ] 新逻辑是否带测试？（纯函数必须有单元测试，UI 交互至少覆盖决策函数）
- [ ] 测试是否覆盖了错误分支与边界，而非只测 happy path？
- [ ] 测试是否真的在断言行为，而不是「跑一遍不报错」？

#### ⑥ 平台兼容

- [ ] 是否只写了 macOS 路径，却让 `linux/`、`windows/` 骨架编译失败？
- [ ] 是否引入了新的系统依赖（需要 brew / 特定版本 Xcode）而未在文档说明？
- [ ] 是否破坏了 Finder 扩展与主 App 之间的文件桥协议？

### 2.3 分语言专项检查

#### Rust（`src-tauri/`）

- [ ] 是否出现 `unsafe`？若有，是否注释了不变量与理由？
- [ ] 错误处理：是否吞掉了 `Result`/`Option`？`unwrap()`/`expect()` 是否只用在「不可能失败」处？
- [ ] 并发：锁的持有范围是否最小化？是否有死锁可能？共享状态是否用对了 `Mutex`/`RwLock`/`Atomic`？
- [ ] 资源释放：文件句柄、连接是否依赖 RAII 正确释放？
- [ ] 该用 `&str` 的地方是否用了 `String`（不必要的分配）？
- [ ] 是否遵循已有的分层约定（`core/` 纯逻辑，平台相关在 `macos/` 等目录）？

#### TypeScript / React（`src/`）

- [ ] Hook 依赖数组是否正确，是否引入陈旧闭包或死循环？
- [ ] 列表渲染的 `key` 是否稳定唯一？
- [ ] 副作用是否清理（`useEffect` 返回清理函数、事件监听移除）？
- [ ] 状态更新是否可能用「渲染时的旧值」覆盖新值？
- [ ] 类型是否用了 `any` 逃避检查？能推导的不要手写。

## 三、审查流程

### 3.1 角色与职责

| 角色 | 职责 |
| --- | --- |
| **作者（Author）** | 自审 → 小 PR → 用模板写清动机与风险 → CI 绿 → 回复每一条审查意见 |
| **审查者（Reviewer）** | 按六维清单找实质问题，标注等级，一次给全，教学式评论 |
| **维护者（Maintainer）** | 合并决策、紧急放行、仲裁分歧 |

单人项目时，Author 与 Reviewer 是同一人：此时「审查」退化为**冷读自审**（隔一段时间再回看，或用 AI 辅助按清单过一遍），流程重点落在自动化门禁上。

### 3.2 PR 生命周期

```
作者自审 + 本地门禁通过
        │
        ▼
创建 PR（用模板，填动机/测试/风险）
        │
        ▼
CI 自动运行（test + clippy + build）──失败──▶ 作者修复
        │ 通过
        ▼
指派审查者，审查者按六维清单 review
        │
        ▼
作者逐条回复：已修复 / 不改（附理由）
        │
        ▼
审查者确认 → Approve
        │
        ▼
Squash 合并到 main
```

### 3.3 硬性规则

1. **PR 大小**：> 400 行（不含测试与生成物）必须拆小或给出合理说明。
2. **响应时效**：审查意见提出后 48 小时内作者须回复；审查者在被指派后 48 小时内完成首轮 review。
3. **批准门槛**：
   - 单人：CI 绿 + 自审清单勾完。
   - 2–3 人小团队：1 名审查者 Approve + CI 绿。
   - 更大团队：涉及 `core/` 与安全相关改动需 2 名 Approve。
4. **紧急放行（bypass）**：仅限线上事故 hotfix，需在 PR 描述注明原因，合并后 24 小时内补审查。
5. **合并方式**：一律 `Squash and merge`，保持 `main` 历史线性可读。

### 3.4 自动化门禁

现有 CI 已覆盖（`.github/workflows/ci.yml`）：

| 门禁 | 命令 | 拦截什么 |
| --- | --- | --- |
| Rust 测试 | `cargo test --all-targets` | 逻辑回归 |
| Rust lint | `cargo clippy --all-targets` | 常见反模式 |
| 前端测试 | `npm test`（vitest） | 纯函数 / 状态机回归 |
| 前端构建 | `npm run build`（tsc + vite） | 类型错误、编译失败 |

**建议补强**（在 GitHub 仓库 Settings 开启 Branch protection）：
- `main` 分支要求 PR + 状态检查通过后才能合并；
- 要求至少 1 次 review 批准（多人协作时）；
- 拒绝直接 push 到 `main`。

**建议新增 lint 门禁**（当前缺 rustfmt 检查与前端 eslint）：见「六、落地清单」。

### 3.5 本地自审命令（作者提交前必跑）

```bash
# Rust
cd src-tauri
cargo fmt --check
cargo clippy --all-targets
cargo test --all-targets

# 前端
npm test
npm run build
```

## 四、评论规范

一条好的审查评论应具备四要素：**定位 + 为什么 + 建议 + 等级**。

> 🔴 **Security: XSS 风险**
> `src/components/Preview.tsx` 第 42 行：剪贴板 HTML 直接 `dangerouslySetInnerHTML`，未过 `sanitizeHtml`。
>
> **Why:** 剪贴板内容是外部不可信输入，攻击者可复制一段带 `<img onerror>` 的 HTML 触发脚本执行。
>
> **Suggestion:** 改用 `sanitizeHtml` 过滤后再渲染，参考 `src/lib/sanitize.ts`。

禁止的写法：

- ❌ 「这代码有问题」——没有定位、没有为什么。
- ❌ 「改成 X」——命令式，不解释理由。
- ❌ 「风格不统一」——没有工具覆盖时也请具体到行与建议。

要求：

1. 每条评论具体到行号或函数。
2. 先说清「为什么」，再给建议。
3. 建议而非命令：用「考虑用 X，因为 Y」。
4. 有值得肯定的地方，明确表扬——好的审查同时指出「这里做得好」。
5. 分级标记 🔴 / 🟡 / 💭 始终出现。

## 五、评分卡（可选，用于周期性质量回顾）

对单个 PR 或里程碑，可沿用在用的评估维度做量化（0–10）：

| 维度 | 权重 |
| --- | --- |
| 功能完整性 | 20% |
| 安全与隐私 | 20% |
| 代码质量 / 可维护性 | 20% |
| 架构设计 | 15% |
| 测试覆盖 | 15% |
| 工程化（CI / 文档） | 10% |

> 本仓库基线评分见《ClipBase 软件评估》（8.2 / 10）。周期回顾时用同一张卡对比变化趋势。

## 七、附录：审查评论速查

- 🔴 安全漏洞 / 数据丢失 / 竞态 / 破坏契约 / 关键路径缺错误处理 → **必须修**
- 🟡 缺校验 / 命名乱 / 缺测试 / N+1 / 重复代码 → **应修，可说明理由不改**
- 💭 风格 / 微命名 / 文档 / 替代方案 → **可选**

**记住一句话：审查的目标是让下一个读这段代码的人（很可能是 6 个月后的你）少踩一个坑。**
